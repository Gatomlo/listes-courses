# Le Cabas (listes-courses)

## Objectif
Outil privé du foyer : listes de courses partagées (« À prévoir » + listes datées), prix moyens par magasin (Intermarché, Colruyt), conseil de magasin et économie estimée du split, listes par magasin triées par rayon, menus qui alimentent les listes. Spécifications : `CAHIER_DES_CHARGES.md` (§11 = étapes). Maquette de référence (toutes les fonctions) : `maquette/index.html`, publiée sur https://claude.ai/artifact/PFxn57TQBfrCebd4mEvCtw (republier après modification ; servir avec `npx http-server maquette -p 5180`). Maquette de refonte v2 (smartphone first, interactive, non codée dans l'app) : `maquette/v2/` (index.html + style.css + data.js, app.js, courses.js, menu.js, more.js, ideas.js), publiée sur https://claude.ai/artifact/PqRcnDnxCtf7kYMUbWoWEn (`/v2/` avec http-server).

## Stack
Node ≥ 22.5, Express 4, `node:sqlite` (base unique `data/cabas.db`), nodemailer. Front : SPA en modules ES sans framework ni build (`public/app/`), navigation par `#/…`. Même socle que MyLittleLibraryV2 (s'en inspirer).

## Règles non évidentes
- **CSP stricte** : aucun script ni `onclick` en ligne → boutons `data-a="action"` (+ `data-*`) traités par `on('click', 'action', fn)` ; champs `data-in` / `data-ch` / `data-enter`. Texte affiché : toujours `esc()`.
- Prix en **centimes** entiers. Prix moyen = N derniers relevés hors promo < 6 mois (`catalog.averages`, fenêtre SQL).
- Droits : toute route `/api/h/:hid/...` passe par `householdMember` ; gestion → `manager` sur la route. Les membres peuvent créer un produit et ajouter un relevé.
- Au moins un gestionnaire par foyer, au moins un magasin actif. **Rayons par magasin** : rayons communs au foyer (`categories`), chaque magasin n'en a qu'une partie, dans son ordre (`store_category_order` = parcours ; `PUT /stores/:sid/order` = liste des rayons du magasin, absents retirés de ce magasin seulement). Nouveau magasin : rayons copiés d'un magasin (`copy_from`, défaut le premier) ou aucun (`'none'`, ex. pharmacie). Nouveau rayon : fin de parcours des magasins `store_ids` (défaut tous). Article d'un rayon absent du magasin : affiché après les rayons du parcours.
- Listes : un article par produit et par liste (ajout = quantités cumulées) ; membre : ajoute en suggestion, coche, modifie quantité/note ; gestionnaire : le reste. Récurrence n = absent des n−1 listes datées précédentes. Clôture : non achetés → liste suivante (défaut) / À prévoir / abandon (`carried_to`), suggestions en attente abandonnées. Suppression d'un produit : retiré des listes en cours, relevés supprimés ; s'il figure dans une liste clôturée il est seulement marqué `deleted_at` (exclu partout, affiché barré dans l'historique, nom de nouveau libre).
- **Menus** = périodes (`menus` : start → end, sans chevauchement) ; une date hors menu enregistré tombe dans une période proposée (`menuPeriod`) : tranches de `menu_days` jours (défaut 15) depuis le lendemain du menu précédent, sinon en remontant depuis le suivant, sinon depuis le dernier `menu_start_dow` (défaut lundi) ; coupée avant le menu suivant. Les repas restent indépendants des menus (clé date × créneau). Déplacer un repas vers un créneau occupé par un repas validé = échange (glisser-déposer sur PC, appui long puis glisser sur téléphone ; plus de « Déplacer » dans la fiche repas). Fiche repas allégée : un seul bouton « Fiche du plat » (recette, mode cuisine, modifier = depuis la fiche) ; « Remettre en envie » (gestionnaire, `POST /meals/:id/wish` : repas retiré, plat en envie ; refusé si le plat est prévu un autre jour). Carte d'envie : bouton vers la fiche du plat.
- une liste datée couvre les repas jusqu'à la veille de la suivante ; split conseillé si économie ≥ seuil.
- Magasin retenu d'un article = `store_id` manuel s'il est actif, sinon conseil, sinon 1er magasin actif. Scénarios : prix inconnu dans un magasin → meilleur prix connu ailleurs, compté « non estimé » ; hors suggestions, indisponibles, supprimés. Split conseillé si ≥ 2 magasins utilisés et économie ≥ seuil.
- Hors-ligne : seules les actions du mode courses passent par des **opérations** (`item.update`, `item.add`, `record.add`, avec `op_id` unique → `applied_ops`) ; le reste exige le réseau (`attempt` affiche « Pas de réseau »). Conflits : « acheté » l'emporte, sinon la plus récente (`at` de l'appareil vs `updated_at`). Lectures : `get()` garde une copie `localStorage` (`cabas-get:<url>`), effacée à la déconnexion. `sw.js` : changer `VERSION` et `FILES` quand les fichiers de l'interface changent (non vérifié dans le navigateur intégré, qui refuse l'enregistrement).
- Ingrédients des repas = vrais articles : `list_items.qty` = part manuelle, `meal_qty` = part repas (détail `list_item_meals`), total affiché = somme ; `syncMealItems(hid)` recalcule toutes les listes ouvertes après tout changement de repas, plat, liste datée ou produit (à appeler dans la transaction). Repas → liste choisie (`list_id`) sinon période (date de la liste → veille de la suivante ; la dernière couvre le rythme). Arrondi à l'emballage supérieur. Retirer un article de repas = le mettre en réserve (`planned_meal_skips`), sinon il reviendrait. Plat supprimé = masqué (`deleted_at`), repas à venir retirés.
- **Unités des ingrédients** (`lib/units.js`) : `dish_ingredients.unit` NULL = emballages du produit, sinon `g` / `kg` / `ml` / `cl` / `l` / `pc` / `cc` (5 ml) / `cs` (15 ml), gardée telle quelle pour la recette et ramenée à g / ml / pc par `toBase` pour les calculs (`list_item_meals.amount` est en unité de base). La contenance (saisie nombre + unité g/kg/ml/cl/L/pièces → `cont_n`/`cont_u`, stockée en texte « 500 g » ; texte libre accepté à l’import CSV, « 6 x 33 cl », « x12 » ; produit au `kg` = 1000 g, à la `pièce`/`tête`/`botte` = 1 pc) donne la taille d'un emballage (`parseSize`, exposée en `size` sur les produits) ; g ≈ ml ; `products.piece_qty` (poids d'une pièce, facultatif) relie pièces et poids. `syncMealItems` convertit chaque part en emballages fractionnaires, somme, puis arrondit ; sans conversion possible : 1 emballage par recette (« ⚠ contenance ? » sur la fiche plat). `list_item_meals.amount/amount_unit` → `need` (« 600 g ») sur l'article. Import de recette : `amount`/`amount_unit` (kg, cl, c. à s. → `cs`… normalisés ; gousse, pincée = 1 emballage + note). Migrations : une entrée peut être une fonction `(conn) => …`.
- **Tags des plats** : tables `tags` (unique par foyer sur `name_norm`) + `dish_tags` ; saisis librement sur la fiche du plat (`saveDish` avec `tags` : noms, créés à la volée ; sans `tags` = inchangés) ; filtres dans Plats et au choix d'un plat du menu ; gestion dans Foyer (renommer vers un nom existant = fusion, fusionner, supprimer). `S.house.tags` = [{ id, name, dishes }].
- Suppression d'une liste datée : possible même avec des articles cochés ou clôturée ; liste en cours → articles manuels non achetés vers « À prévoir » ; relevés de prix gardés.
- **Envies de plats** (plat déjà au menu — repas validé à venir — : envie refusée, retirée par migration, ignorée par la génération ; « Changer de plat » vers une envie la retire) (`dish_wishes`, sans date, section « 💡 Envies de plats » de l'écran Menu ; badge sur l'onglet Menu = `wishesPending`, hors suggestions de l'écran Listes) : toujours liées à un plat (`dish_id`). Nom libre → plat créé ; proposé par un membre = **fiche brouillon** (`dishes.draft = 1`, `draft_by`, ✏️, filtre « Suggestions » dans Plats), modifiable par son auteur seulement. Membre → `pending` ; gestionnaire + plat validé → `ok`. Validation : ✓ (plat existant), enregistrement du brouillon par un gestionnaire (« Valider la fiche »), ou mise au menu (planifier = valider, `wishDone`). Refus / retrait d'un brouillon = fiche supprimée avec ses suggestions de repas (`dropDraft`). Envies en tête (💡) du choix de plat d'un créneau ; supprimées quand le plat est mis au menu ou supprimé.
- **Variantes de plats** : `dish_options` (groupe `grp` + option) ; `dish_ingredients.option_id` NULL = commun ; choix d'un repas dans `planned_meal_options`, à défaut 1re option de chaque groupe (`chosenOptions`, aussi si l'option choisie a été supprimée). `saveDish` garde les ids d'options envoyés. `mealRows` : `dish` = libellé « Plat · var1, var2 », `dish_name` = nom seul.
- **Plats composés** (ex. Mezze = Houmous + Taboulé + Falafels) : `dish_parts (dish_id, part_id, portions, position)`, un seul niveau (ni composé dans un composé, ni composant qui devient composé) ; chaque composant reste un plat normal. `portions` = portions du composant pour les portions du plat composé ; facteur au repas = persons / portions du composé × portions / portions du composant (`mealUnits`, variantes du composant par défaut). Le composé peut avoir ses propres ingrédients (« Ingrédients en plus »). Repas : « pas cette fois » par composant (`planned_meal_part_skips`, `part_skip`). `syncMealItems` additionne les recettes (une part `list_item_meals` par produit et repas, quantité réelle gardée si même unité). Historique / « prévu » d'un composant : compte les repas du composé où il n'est pas écarté (`via`). `saveDish` avec `parts` (sans = inchangée) ; composant supprimé = retiré des compositions. API : `parts` (fiche complète des composants), `used_in` sur la fiche, `parts`/`part_names` dans la liste, `parts`/`part_skip` sur les repas.
- **Photos des plats** : `dishes.photo` = fichier dans `<données>/photos` (sauvegarder ce dossier avec la base) ; servie par `GET /api/h/:hid/dishes/:did/photo` (connexion requise, adresse `photo` changée à chaque photo). Enregistrement du plat avec `photo_data` (data URL jpeg/png/webp, redimensionnée à 1280 px par l'appareil, 3 Mo max), `photo_url` (photo de la recette importée, téléchargée par le serveur avec les garde-fous SSRF) ou `photo: null`. Vignettes `tile(nom, pastilles, classe, photo)`.
- **Import de recette** : cuillères (« C. à café », « c. à s. », « càs », « cuillerée à café »…) → `cc` / `cs` (`SPOON` dans `recipes.js`) ; `image` lue dans le JSON-LD ; à l'écran d'import chaque ingrédient est un nom modifiable avec liste des produits (nom existant = relié, sinon nouveau produit, rayon au choix).
- **Produits en masse** (PC, gestionnaire) : cases à cocher, `POST /products/bulk` `{ ids, set: { category_id | is_base | forced_store_id | recurrence } }` ou `{ ids, delete: true }`.
- Création d'un plat depuis le menu : `S.dishReturn = { date, slot }` → après enregistrement retour au menu et reprise de l'ajout du repas.
- Accordéons : état en `localStorage`, séparé mobile/PC ; sur PC ouverts par défaut (sauf `def: 'closed'`).
