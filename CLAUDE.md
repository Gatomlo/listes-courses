# Le Cabas (listes-courses)

## Objectif
Outil privé du foyer : listes de courses partagées (« À prévoir » + listes datées), prix moyens par magasin (Intermarché, Colruyt), conseil de magasin et économie estimée du split, listes par magasin triées par rayon, menus qui alimentent les listes. Spécifications : `CAHIER_DES_CHARGES.md` (§11 = étapes). Maquette de référence (toutes les fonctions) : `maquette/index.html`, publiée sur https://claude.ai/artifact/PFxn57TQBfrCebd4mEvCtw (republier après modification ; servir avec `npx http-server maquette -p 5180`).

## État (au 2026-10-02)
- **Étape 1 (socle) codée** : connexion par lien e-mail, foyers, membres et invitations, rôles, réglages, magasins (couleur, actif), rayons et leur ordre par magasin, produits — ex-« Catalogue », route interne `#/catalogue` inchangée (fiche, relevés, prix moyens, magasin conseillé/imposé, fusion, suppression). Interface mobile + PC (barre latérale, accordéons, colonnes en maçonnerie).
- **Étape 2 (listes) codée** : « À prévoir » (créée à la demande), listes datées (une par date, date proposée = dernière + rythme), import des récurrents dus et d'articles « À prévoir », ajout avec recherche/création de produit, quantités cumulées, coche « acheté », fiche article (quantité, note, indisponible, déplacer, récurrent, retirer), suggestions des membres (validation dans la liste ou Foyer, badge), menu ⋯ (date, statut, clôture avec report par article, suppression), historique en lecture seule + copie vers « À prévoir ».
- **Étape 3 (prix) codée** : prix effectif par article et magasin (promo valable sinon moyenne), magasin conseillé (imposé > moins cher), choix manuel par article (étiquette cliquable, tout membre ; retour au conseil), « tout chez X » (gestionnaire), scénarios + économie vs seuil, détail d'une liste datée : encadré « Scénarios comparés » en tête (économie, « Tout chez X » / « Conseil ») puis filtre Tous / magasin (`S.q.listStore`, par liste ; rayons dans l'ordre du magasin, bouton vers le mode courses) ; plus d'onglets Magasins ni Repas ; ajout par bouton flottant ＋ (panneau) ; un article = une ligne (prix, détails dans la fiche, plats via 🍽) ; écran Listes : estimation du panier (`summary` → `estimate`), promos (sortie ou date, prix facultatif, une par produit × magasin, tout membre). Suggestions en attente : accordéon en haut de l'écran Listes + badge onglet Listes.
- **Étape 4 (mode courses, temps réel, hors-ligne) codée** : mode courses `#/listes/:id/magasin/:sid` (rayons du magasin, gros texte, « Dans le caddie », prix payé facultatif au cochage → relevé `check`, « Terminer » : non pris → indisponibles), présence (« Léa est aussi sur cette liste ») et rechargement en direct par SSE, hors-ligne (copie locale de chaque lecture, file d'opérations rejouée au retour du réseau, bandeau), service worker `public/sw.js`.
- **Étape 5 (scan du ticket) codée** : photo (« Terminer chez X » ou liste clôturée) → image préparée → Tesseract.js sur le téléphone (fichiers servis par l'app depuis `node_modules` sous `/vendor/…`) → `ticket.mjs` (lignes, quantités, remises = promo, date, magasin ; rapprochement : correspondance mémorisée par magasin, sinon ressemblance des mots + bonus liste) → écran de validation (libellé, quantité, prix, promo, produit / créer / ignorer) → opération `receipt.save` (relevés `ocr`, articles cochés, produits créés, correspondances mémorisées ; marche hors-ligne).
- **Étape 6 (plats et menus) codée** : plats (fiche en accordéons, ingrédients en emballages, recette facultative, import depuis un lien via JSON-LD schema.org/Recipe, historique 5 dernières fois), menu (jours × créneaux, grille semaine sur PC, repas affichés au choix via une modale — `cabas-menu-slots` en localStorage ; actions dates / repas affichés / export dans la barre du haut, menu ☰ sur téléphone), ajout avec personnes et ingrédients en réserve, fiche repas (recette ajustée, rattachement de liste, changer de plat), suggestions de repas des membres, ingrédients dans les listes (fusion « pour X, Y », placards, onglet Repas, « déjà en réserve »), export A4 + impression/PDF navigateur (semaines de 7 colonnes égales, encadré « Remarques » : texte `menu_notes` par premier jour affiché, sinon cadre ligné vide à remplir à la main), lien d'affichage public révocable (`#/affichage/:token`).
- **Connexion sans e-mail** (le serveur de prod n'envoie pas de mails) : e-mail + mot de passe, premier compte libre tant qu'il n'y a aucun compte, inscription par lien d'invitation, réinitialisation par lien créé par un gestionnaire, `npm run set-password`. E-mails désactivés par défaut (`CABAS_MAIL` = off | log | smtp | sendmail ; `SMTP_HOST` ⇒ smtp).
- Toutes les étapes du §11 sont codées. Reste : essais réels (téléphone, tickets, sites de recettes), mise en ligne.
- Décisions : nom « Le Cabas », seuil 5 €, prix comparés par emballage (contenance facultative), OCR Tesseract.js, pas de total ticket ni lien budget-foyer, pas de sous-domaine (`/cabas` sur le domaine de la passerelle). Point ouvert : coût fixe 2e magasin (défaut : non).

## Stack
Node ≥ 22.5, Express 4, `node:sqlite` (base unique `data/cabas.db`), nodemailer. Front : SPA en modules ES sans framework ni build (`public/app/`), navigation par `#/…`. Même socle que MyLittleLibraryV2 (s'en inspirer).

## Fichiers clés
- `server.js` : exporte `app` (listen seulement si lancé directement), page `index.html` avec `{{ROOT}}` → `<base href>`, API sur `/api`.
- `lib/db.js` : connexion, `tx`, `normalize`, migrations (`MIGRATIONS`, `PRAGMA user_version` ; ne jamais modifier une entrée déployée).
- `lib/auth.js` : mots de passe (scrypt, limiteur d'échecs), liens de réinitialisation, lien de connexion par e-mail (optionnel), sessions 90 j (cookie `cabas_session`, `Path=<montage>/`), gardes `householdMember` / `manager`.
- `lib/api.js` : toutes les routes ; `lib/households.js` (foyer, membres, invitations) ; `lib/catalog.js` (magasins, rayons, produits, relevés, prix moyens) ; `lib/lists.js` (listes, articles, suggestions, clôture, récurrents, promos) ; `lib/pricing.js` (prix effectifs, magasin retenu, scénarios) ; `lib/sync.js` (rejeu d'opérations, conflits) ; `lib/events.js` (SSE, présence, diffusion après chaque modification) ; `lib/receipts.js` (tickets, correspondances `store_aliases`) ; `lib/meals.js` (plats, repas, recalcul des ingrédients `syncMealItems`, lien d'affichage) ; `lib/recipes.js` (import de recette, garde-fous SSRF) ; `lib/csvimport.js` (import CSV de produits + relevés : en-têtes nom;rayon;emballage;contenance;magasin;prix;promo;prix normal;date, aperçu `dry` en transaction annulée, relevé identique ignoré) ; `lib/mailer.js` ; `lib/security.js` (CSP, `jsonOnly`).
- `public/app/` : `main.js` (démarrage, routes, cadre), `ui.js` (esc, accordéons, panneau, toast, actions), `api.js`, `state.js`, un fichier par écran (`connexion.js`, `foyer.js` (membres, réglages, tags), `magasins.js` (magasins, ordre des rayons, rayons), `catalogue.js`, `listes.js`, `scan.js`, `plats.js`, `menu.js`) ; `ticket.mjs` (analyse du texte et rapprochement, sans dépendance, testé par node). `install.js` : bouton « Installer l'app » (écran Foyer ; invite du navigateur si disponible, sinon marche à suivre iPhone / Android / PC ; masqué une fois installée).

## Règles non évidentes
- **CSP stricte** : aucun script ni `onclick` en ligne → boutons `data-a="action"` (+ `data-*`) traités par `on('click', 'action', fn)` ; champs `data-in` / `data-ch` / `data-enter`. Texte affiché : toujours `esc()`.
- Prix en **centimes** entiers. Prix moyen = N derniers relevés hors promo < 6 mois (`catalog.averages`, fenêtre SQL).
- Droits : toute route `/api/h/:hid/...` passe par `householdMember` ; gestion → `manager` sur la route. Les membres peuvent créer un produit et ajouter un relevé.
- Au moins un gestionnaire par foyer, au moins un magasin actif. Nouveau rayon = fin de parcours de tous les magasins.
- Listes : un article par produit et par liste (ajout = quantités cumulées) ; membre : ajoute en suggestion, coche, modifie quantité/note ; gestionnaire : le reste. Récurrence n = absent des n−1 listes datées précédentes. Clôture : non achetés → liste suivante (défaut) / À prévoir / abandon (`carried_to`), suggestions en attente abandonnées. Suppression d'un produit : retiré des listes en cours, relevés supprimés ; s'il figure dans une liste clôturée il est seulement marqué `deleted_at` (exclu partout, affiché barré dans l'historique, nom de nouveau libre).
- **Menus** = périodes (`menus` : start → end, sans chevauchement) ; une date hors menu enregistré tombe dans une période proposée (`menuPeriod`) : tranches de `menu_days` jours (défaut 15) depuis le lendemain du menu précédent, sinon en remontant depuis le suivant, sinon depuis le dernier `menu_start_dow` (défaut lundi) ; coupée avant le menu suivant. Les repas restent indépendants des menus (clé date × créneau). Déplacer un repas vers un créneau occupé par un repas validé = échange (glisser-déposer sur PC, « Déplacer » dans la fiche repas).
- une liste datée couvre les repas jusqu'à la veille de la suivante ; split conseillé si économie ≥ seuil.
- Magasin retenu d'un article = `store_id` manuel s'il est actif, sinon conseil, sinon 1er magasin actif. Scénarios : prix inconnu dans un magasin → meilleur prix connu ailleurs, compté « non estimé » ; hors suggestions, indisponibles, supprimés. Split conseillé si ≥ 2 magasins utilisés et économie ≥ seuil.
- Hors-ligne : seules les actions du mode courses passent par des **opérations** (`item.update`, `item.add`, `record.add`, avec `op_id` unique → `applied_ops`) ; le reste exige le réseau (`attempt` affiche « Pas de réseau »). Conflits : « acheté » l'emporte, sinon la plus récente (`at` de l'appareil vs `updated_at`). Lectures : `get()` garde une copie `localStorage` (`cabas-get:<url>`), effacée à la déconnexion. `sw.js` : changer `VERSION` et `FILES` quand les fichiers de l'interface changent (non vérifié dans le navigateur intégré, qui refuse l'enregistrement).
- Ingrédients des repas = vrais articles : `list_items.qty` = part manuelle, `meal_qty` = part repas (détail `list_item_meals`), total affiché = somme ; `syncMealItems(hid)` recalcule toutes les listes ouvertes après tout changement de repas, plat, liste datée ou produit (à appeler dans la transaction). Repas → liste choisie (`list_id`) sinon période (date de la liste → veille de la suivante ; la dernière couvre le rythme). Arrondi à l'emballage supérieur. Retirer un article de repas = le mettre en réserve (`planned_meal_skips`), sinon il reviendrait. Plat supprimé = masqué (`deleted_at`), repas à venir retirés.
- **Unités des ingrédients** (`lib/units.js`) : `dish_ingredients.unit` NULL = emballages du produit, sinon `g` / `ml` / `pc`. La contenance (saisie nombre + unité g/kg/ml/cl/L/pièces → `cont_n`/`cont_u`, stockée en texte « 500 g » ; texte libre accepté à l’import CSV, « 6 x 33 cl », « x12 » ; produit au `kg` = 1000 g, à la `pièce`/`tête`/`botte` = 1 pc) donne la taille d'un emballage (`parseSize`, exposée en `size` sur les produits) ; g ≈ ml ; `products.piece_qty` (poids d'une pièce, facultatif) relie pièces et poids. `syncMealItems` convertit chaque part en emballages fractionnaires, somme, puis arrondit ; sans conversion possible : 1 emballage par recette (« ⚠ contenance ? » sur la fiche plat). `list_item_meals.amount/amount_unit` → `need` (« 600 g ») sur l'article. Import de recette : `amount`/`amount_unit` (kg, cl, c. à s.… normalisés ; gousse, pincée = 1 emballage + note). Migrations : une entrée peut être une fonction `(conn) => …`.
- **Tags des plats** : tables `tags` (unique par foyer sur `name_norm`) + `dish_tags` ; saisis librement sur la fiche du plat (`saveDish` avec `tags` : noms, créés à la volée ; sans `tags` = inchangés) ; filtres dans Plats et au choix d'un plat du menu ; gestion dans Foyer (renommer vers un nom existant = fusion, fusionner, supprimer). `S.house.tags` = [{ id, name, dishes }].
- Suppression d'une liste datée : possible même avec des articles cochés ou clôturée ; liste en cours → articles manuels non achetés vers « À prévoir » ; relevés de prix gardés.
- **Variantes de plats** : `dish_options` (groupe `grp` + option) ; `dish_ingredients.option_id` NULL = commun ; choix d'un repas dans `planned_meal_options`, à défaut 1re option de chaque groupe (`chosenOptions`, aussi si l'option choisie a été supprimée). `saveDish` garde les ids d'options envoyés. `mealRows` : `dish` = libellé « Plat · var1, var2 », `dish_name` = nom seul.
- Création d'un plat depuis le menu : `S.dishReturn = { date, slot }` → après enregistrement retour au menu et reprise de l'ajout du repas.
- Accordéons : état en `localStorage`, séparé mobile/PC ; sur PC ouverts par défaut (sauf `def: 'closed'`).

## Commandes
- CSP : `script-src 'self' 'wasm-unsafe-eval'` (Tesseract) ; tout reste servi par l'app (aucun CDN pour l'OCR).
- Paniers transcrits à importer : `imports/*.csv` (Produits → ⇪ Importer).
- Icônes d'installation (PNG iPhone/Android, dont `maskable`) : `python scripts/make-icons.py` (Pillow) les régénère depuis le dessin de `public/icon.svg`.
- `npm test` (API sur base temporaire, e-mails en mémoire ; `tests/helpers.js` : clients, foyer gestionnaire + membre).
- Essai local : `CABAS_DATA_DIR=<dossier temp> CABAS_MAIL=log PORT=3101 node server.js` → le lien de connexion s'affiche dans la console. Ne jamais essayer sur `data/`.
- Passerelle locale : jonction `node-gateway/apps/cabas` → ce dossier (créée), servie sur `http://localhost:3000/cabas/`.

## Dépôt
GitHub privé : https://github.com/Gatomlo/listes-courses (branche `master`) ; pousser après chaque commit.

## Déploiement (Infomaniak, via node-gateway)
Envoyer `server.js`, `package.json`, `package-lock.json`, `lib/`, `public/` dans `apps/cabas` (jamais `data/`), `npm install --omit=dev`, redémarrer. Variables : `CABAS_PUBLIC_URL` (ex. `https://<domaine>/cabas`, recommandée : adresse des liens d'invitation et de réinitialisation) ; e-mails facultatifs : `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`MAIL_FROM` ou `CABAS_MAIL=sendmail`. Mot de passe de secours : `npm run set-password -- <email> <mdp>`. Migrations automatiques au démarrage.

## Méthode
Réponses en français, concises. Une étape du §11 à la fois ; après chaque modification `npm test` ; tester par l'API avant l'interface ; commit après chaque fonctionnalité validée.
